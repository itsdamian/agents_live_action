# 未來開發規劃（Roadmap）

> 排序原則：**商業價值優先、使用便利性優先**。
> 每個階段結束時都要有「可以拿出去 demo / 實際使用」的成果，避免長期停留在工程重構而看不到使用者價值。

## 現況盤點（2026-07）

| 已完成 | 未完成 |
|---|---|
| 資料模型、環境變數管理（tasks 1–2） | 流水線排程器（task 7） |
| 專案掃描、agent YAML 配置（task 3） | REST API + WebSocket（task 8） |
| 任務檔案監控與回寫（task 4） | `main.py` 整合啟動流程（task 9） |
| LLM 抽象層（**僅 mock 可用**，真實 provider 是空框架）（task 5） | Vue 3 前端（task 10） |
| 四個 agent 類別 + 完整單元測試（task 6） | |

**關鍵缺口**：系統目前無法端到端運行；agent 只會產生 mock 文字，沒有真實 LLM 呼叫，產出也只寫進 log，不落地成實際可用的檔案。

## Phase 0：打通 MVP —— 讓系統真的能動（最優先，約 1–2 週）

商業邏輯：沒有能跑的產品就沒有任何商業價值。目標是最短路徑做出「放任務進去 → 看到流水線動 → 拿到結果」的完整體驗。

1. **完成流水線排程器**（原 task 7）
   - PriorityQueue、PM → SWE → QA、重工邏輯、事件廣播。
2. **完成 REST API + WebSocket**（原 task 8）
   - `GET /api/projects`、`GET /api/projects/{id}/tasks`、`WS /ws/{project_id}`。
   - 額外加入 `POST /api/projects/{id}/tasks`（原規格沒有，但這是便利性關鍵，見 Phase 1-3）。
3. **完成 `main.py` 整合**（原 task 9）
   - 啟動掃描 → 建立預設 agents → TaskWatcher → DevOps 週期監控。
4. **前端：改造現有 vanilla JS 接上 WebSocket，暫緩 Vue 重構**
   - ⚠️ 調整原規劃：task 10 的 Vue 3 重寫是工程驅動而非使用者價值驅動。現有 `index.html` + `js/` 動畫已完整，先加一層 WS client + 專案選單即可上線 demo，省下約一週工時。
   - Vue 重構移到 Phase 2（UI 複雜度成長到值得重構時再做）。
5. **內建範例專案 + Quickstart**
   - `projects/example-project/`（含 `tasks.yaml` 範例）隨 repo 提供，`docker compose up` 後 30 秒內就能看到流水線在動。README 提供三步驟上手指南。

**驗收標準**：全新使用者 clone 下來，`docker compose up`，不設任何 API key，就能在瀏覽器看到 mock 模式流水線完整跑完一個範例任務。

## Phase 1：真實價值 —— 從展示品變成工具（約 2–3 週）

商業邏輯：mock 模式只能 demo，不能收費也留不住使用者。這個階段讓平台產生「真的幫使用者做事」的價值。

1. **接通真實 LLM API**（最高商業價值）
   - 補完 `AnthropicClient` / `OpenAIClient` 的實際呼叫（目前 `llm_client.py` 只留了註解位置）。
   - 支援逾時、重試、rate-limit 處理；失敗時降級不中斷流水線。
2. **Agent 產出落地成檔案**
   - SWE agent 的程式碼產出寫入 `projects/{name}/deliverables/{task_id}/`，而不是只存在 log 裡。
   - PM 的計畫、QA 的測試報告同樣落地為 markdown。使用者拿得到成果，價值才成立。
3. **UI 直接新增任務**（最高便利性價值）
   - 目前唯一的進任務方式是手動編輯 YAML——這是最大使用門檻。
   - 前端加任務表單（標題、描述、優先級）→ `POST /api/.../tasks` → 回寫 `tasks.yaml`（維持檔案為唯一真相來源，兩種入口並存）。
4. **UI 檢視任務結果**
   - 點擊任務可看各 agent 的輸出、log、產出檔案清單；不用去翻 `logs/` 資料夾。
5. **成本追蹤與預算上限**（商業必備）
   - 記錄每次 LLM 呼叫的 token 用量與估算成本，任務卡與 DevOps 面板顯示累計花費。
   - 可設每日/每專案預算上限，超過即暫停流水線並警示——沒有這個，沒人敢把真 API key 交給自動化系統。

**驗收標準**：使用者設定一組 API key，在 UI 上建任務，agents 真實執行並在 `deliverables/` 產出檔案，UI 上看得到過程、結果與花費。

## Phase 2：使用便利性深化 —— 讓人願意天天用（約 3–4 週）

商業邏輯：留存與信任。自動化系統要被日常採用，關鍵是「可控」與「省心」。

1. **Human-in-the-loop 核准關卡**
   - 可設定任務在 SWE 產出後（或 QA 通過後）暫停等待人工核准/退回，UI 一鍵操作。
   - 信任是自動化產品的採用前提，這是商業上的解鎖功能。
2. **任務歷史與統計儀表板（SQLite 持久化）**
   - 任務歷史、成功率、平均耗時、重工率、成本趨勢。YAML 仍是任務入口，DB 負責歷史與統計。
3. **Agent 配置 UI 化**
   - 在 UI 上調整各 agent 的模型、system prompt、並發數，儲存回 YAML；不用開編輯器。
4. **通知整合**
   - 任務完成/失敗/等待核准時推送 Slack webhook 或 email。使用者不需要盯著畫面。
5. **前端重構為 Vue 3**（原 task 10 移到此處）
   - 到這階段 UI 已有表單、任務詳情、核准流、儀表板，複雜度足以回收重構成本。

**驗收標準**：使用者可以早上開好幾個任務、去做別的事、收到通知回來核准，全程不碰任何 YAML 或終端機。

---

## Phase 3：商業化擴張 —— 從個人工具到可販售產品（1–2 個月起）

商業邏輯：擴大目標市場、建立收費依據。依市場回饋挑選順序，不必全做。

1. **Git 整合（差異化關鍵）**
   - Agent 在獨立 branch 上實際修改專案程式碼、commit、開 PR；QA agent 真的執行測試而非只評估文字。這讓平台從「產生建議」升級為「交付可合併的程式碼」，是最強的付費理由。
2. **多使用者與權限**
   - 登入、專案層級權限、API token——進入團隊市場的門票。
3. **專案/Agent 模板庫**
   - 常見專案類型（web app、爬蟲、資料分析）的預設 agent 組合與任務模板，降低新使用者啟動成本。
4. **CI / API 整合**
   - 對外 REST API + webhook，讓 CI 或其他系統觸發任務，平台成為工作流的一環而非孤島。
5. **部署與收費選項**
   - 單機版（現有 Docker）維持免費/開源引流；SaaS 或授權版承載進階功能（多使用者、統計、Git 整合）。

## 原規劃調整摘要

| 調整 | 原因 |
|---|---|
| Vue 3 重構（task 10）從 MVP 延後到 Phase 2 | 工程重構不產生使用者價值；現有動畫前端加 WS client 即可 demo |
| 真實 LLM 呼叫從「留框架」提升為 Phase 1 第一優先 | 沒有真實執行就沒有商業價值 |
| 新增 `POST /tasks`、產出落地、成本追蹤（原規格未涵蓋） | 分別對應最大使用門檻、價值成立、信任門檻三個商業關鍵 |
| DevOps agent 維持現狀，不再擴充 | 監控是輔助功能，先把主流水線價值做滿 |
