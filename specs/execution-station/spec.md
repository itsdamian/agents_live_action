# Spec：執行站（在沙盒裡真的跑程式）

Status: CONFIRMED（2026-11-26 使用者確認；初稿 2026-11-25）

> 相關文件：之後的 `plan.md`、`tasks.md`。
> 基底：`feat/live-action-hud` MVP（動態編制、make／check 站、重做規則、DB 模式、`MOCK_STEP_DELAY_MS`），預計在 MVP 合併到 `dev` 之後開始。
> 起因：2026-11-24 以真實 Claude（Sonnet 5.5）跑 `payment-guardian` 的 tasks.md 第 3 項。SWE 寫出的 Go 程式碼在本機 `go build`／`go vet`／`go test -race` 都通過，但 QA 因為拿不到任何執行輸出，連續 4 次判 FAIL，任務以「QA still failing after 3 reworks」失敗，花費 0.30 美元。

## Summary

目前流水線裡的 agent 只能讀寫文字，QA 只能審查程式碼、無法驗證它真的能編譯和通過測試，於是會因為「缺執行證據」而無限退件。本功能新增一種**不用 LLM 的站點類型「執行站」**：把專案原始碼加上 SWE 這次的修改，放進一次性、隔離的沙盒容器，跑專案設定好的 build／lint／test 指令，把真實輸出交給下游（QA）判斷；指令失敗時依現有重做規則退回 SWE。沙盒由一個獨立的 runner 服務管理，後端拿不到 Docker 權限。這也是之後「agent 在沙盒裡用 tool use 反覆執行」的基礎。

## Goals

1. **真實的執行證據**：QA 的判斷依據包含指令的實際結束碼與輸出，不再只靠審查。
2. **新站點類型 `run`**：和 `make`／`check` 並列，可放進自訂編制；不呼叫 LLM、不產生 LLM 花費。
3. **沙盒隔離**：每次執行用一個全新的容器，沒有網路、有 CPU／記憶體／程序數／時間上限，跑完就刪；專案的機密檔不會進沙盒。
4. **沙盒控制權分離**：由獨立的 runner 服務啟動與管理沙盒；後端只透過內部 API 呼叫它，後端容器不掛 Docker socket。
5. **每個專案自訂工具鏈**：專案設定指定沙盒映像檔與指令清單；附 Go、Python 兩組範本。
6. **SWE 可以建議指令**：SWE 可提出額外指令，經允許清單檢查後才會執行。
7. **與現有流程一致**：失敗依「退回最近的前方 make」重做並計入重做次數；HUD 上看得到執行站在跑哪個指令、結果如何；歷史與重啟行為和其他站一樣。
8. **為 tool use 鋪路**：runner 的 API 以「工作區（workspace）＋多次執行指令」為單位設計，之後的 agent tool use 可以直接沿用。

## Non-Goals

- **agent tool use**（SWE／QA 在沙盒裡自己寫檔、跑指令、反覆修改）：下一份 spec，本功能只提供基礎。
- **修改真實的專案檔案或 git repo**：沙盒裡的修改跑完即丟；不 commit、不開 PR、不寫回 `projects/<p>/`。交付檔照舊寫在 `deliverables/`。
- **沙盒裡連網**：包含下載相依套件。需要相依的專案要用已內建相依的映像檔，或把相依放進專案（vendor）。
- **legacy 引擎與檔案模式**：只支援 LangGraph 引擎＋DB 模式（與動態編制相同）。
- 多台機器、遠端 runner、Kubernetes；Windows 容器。
- 比 Docker 預設隔離更強的沙盒技術（gVisor、Firecracker 等）：列為選配，見 Open Questions。
- 程式碼覆蓋率、效能測試、靜態安全掃描等額外報告。
- 讓 LLM 自由決定任意指令：SWE 只能「建議」，而且要通過允許清單。

## Requirements / User Stories

### 使用者故事

- U1 我在專案設定裡開啟執行，選「Go」範本（映像檔 `golang:<版本>`，指令 `gofmt -l .`、`go build ./...`、`go vet ./...`、`go test ./...`），然後在 SWE 和 QA 之間加一個「執行站」。
- U2 我派一張任務。便條經過 SWE 後到執行站，桌上依序顯示正在跑哪個指令、每個指令過或不過；全部通過時便條帶著執行報告交給 QA。
- U3 某個指令失敗時，執行站把失敗的指令和輸出當成退件意見退回 SWE；SWE 重做後再跑一次。重做次數和 check 站的退件共用同一個上限。
- U4 QA 看得到執行報告，依據實際輸出判斷，不會再因為「沒有執行證據」退件。
- U5 我在任務詳情和便條牆看得到每次執行的指令、結束碼、耗時與輸出（過長時截斷並註明）。
- U6 SWE 在輸出中建議額外指令（例如只跑某個測試），符合允許清單的才會跑，不符合的在報告中標示「未執行：不在允許清單」。
- U7 runner 服務沒啟動或映像檔不存在時，執行站標示「無法執行」並讓任務失敗（附原因），不會卡住流水線，也不會被當成 SWE 的錯而觸發重做。

### 需求

**R1 站點類型 `run`**
- 編制中的 seat 可為 `make`、`check`、`run`；`run` 不呼叫 LLM。
- 合法性：`run` 前方必須至少有一個 `make`。
- 結果只有三種：`passed`（所有必要指令結束碼為 0）、`failed`（有必要指令失敗或逾時）、`error`（基礎設施問題：runner 無法連線、映像檔不存在、工作區建立失敗等）。
- `failed` → 依現有規則退回最近的前方 `make`，計入 `rework_count`，退件意見為執行報告摘要；超過上限時任務失敗，原因 `f"{ID.upper()} still failing after {n} reworks"`（與 check 一致）。
- `error` → 任務直接失敗，原因說明是執行環境問題；不重做。
- 輸出（執行報告）作為下游的上游產出，QA 的 prompt 中會出現。
- 閘門語意：`after_swe` 仍為最後一個 make 之後；`after_qa` 的「最後一個 check 通過之後」不把 `run` 算成 check。

**R2 SWE 輸出改為「檔案清單」**
- 編制中有 `run` 站時，SWE（內建或自訂 make）被要求以可解析的格式輸出「相對路徑＋完整檔案內容」；沒有 `run` 站時 prompt 與輸出格式不變（預設三站編制零差異）。
- 路徑規則：只接受專案內的相對路徑；拒絕絕對路徑、`..`、指向 `.git/`、`.env*` 等機密檔；單檔與總量有上限。被拒絕的項目寫進執行報告。
- 解析不到任何檔案時，執行站結果為 `failed`，退件意見說明格式要求（讓 SWE 有機會修正）。
- 同一任務重做時，以 SWE 最新一版的檔案清單為準。

**R3 沙盒工作區內容**
- 專案 `projects/<p>/` 的副本，排除：`deliverables/`、`logs/`、`.git/`、`.env*`、`agents/`、專案設定中額外列出的排除項目；之後疊上 SWE 這次的檔案（同路徑覆蓋）。
- 原始的 `projects/<p>/` 永遠不被修改。

**R4 專案的執行設定**
- 每個專案一份執行設定：是否啟用、映像檔、依序執行的指令（每個指令為參數陣列，不經 shell）、每個指令是否為必要、每個指令與整體的時間上限、額外排除路徑、SWE 建議指令的允許清單（允許的執行檔名）。
- 在 HUD 上可檢視與修改；修改的生效時機比照編制（閒置立即、否則任務結束後）。
- 映像檔必須在允許清單內（預設只有範本用到的映像檔），避免任意映像檔。
- 附 Go、Python 兩組範本。

**R5 SWE 建議指令**
- SWE 可在輸出中列出建議指令（同樣是參數陣列）；執行站在設定的指令之後執行通過檢查的建議指令。
- 檢查：第一個參數必須在允許清單；數量有上限；不經 shell。
- 建議指令一律不是「必要」：失敗會寫進報告並交給 QA 判斷，但不會單獨觸發退件。

**R6 沙盒限制**
- 無網路；非 root 使用者；根檔案系統唯讀，只有工作區與暫存目錄可寫；CPU、記憶體、程序數上限；每個指令與整體都有時間上限，逾時強制停止並記為失敗；跑完（含失敗、逾時、取消）一定刪除容器與工作區。
- 每個指令的輸出有大小上限，超過時保留開頭與結尾並註明截斷；交給 QA 的報告另有較小的上限。
- 沙盒拿不到任何 API 金鑰或後端的環境變數。

**R7 runner 服務**
- 獨立的服務與容器，只有它能控制 Docker；後端容器不掛 Docker socket。
- 只在 compose 內部網路提供 API，需共用密鑰驗證；不對主機開 port（除非明確設定）。
- API 以工作區為單位：建立工作區（上傳檔案）→ 執行一個或多個指令（可逐步回報進度）→ 刪除工作區；工作區有存活時間上限，逾時自動清除（避免後端重啟後留下孤兒容器）。
- 同時執行的工作區數量有上限，超過時排隊。
- 啟用方式：compose 的選用 profile；沒有啟用時三步驟 quickstart 與 Mock 體驗完全不變。

**R8 Mock 與強制 Mock**
- `FORCE_MOCK=true` 或專案 LLM 為 Mock 時，Mock SWE 在有 `run` 站時輸出一組範本內的小檔案清單；執行站仍實際送 runner 執行（執行本身不花錢）。
- 另提供「假 runner」模式（不需 Docker，依設定回傳固定結果，可設定第一次失敗），供測試、replay 錄製與沒有 runner 的 Docker 示範使用。
- `MOCK_STEP_DELAY_MS` 不套用在真實執行上；假 runner 套用。

**R9 事件、歷史與畫面**
- 執行站發 `station:update`（與其他站相同語意）與 `agent:phase`（例如「準備工作區」、「執行 `go test ./...`（3/4）」、「清理」）；可串流指令輸出的節流片段（比照 token 節流）。
- `task_run_steps` 記錄每次執行的指令、結束碼、耗時、是否截斷；完整輸出寫成交付檔（例如 `NN_run_report.md`）。
- HUD：執行站有獨立造型與「指令進度」顯示；任務詳情有執行報告分頁；新增 agent 表單可選 `run`。
- 既有事件與欄位不刪不改語意；預設三站編制的事件序列逐筆相同。

**R10 重啟與取消**
- 後端在執行站執行中重啟：重啟時 `in_progress` 的任務依現行規則標 failed；runner 端的工作區由存活時間上限清除。
- runner 在執行中重啟：執行站結果為 `error`。

## Acceptance Criteria

- **AC1 預設零差異**：預設三站編制、沒有 `run` 站時，既有測試全綠，事件序列與 SWE prompt 逐筆相同。
- **AC2 通過流程**：Go 範本、編制 PM → SWE → 執行站 → QA，以假 SDK 物件讓 SWE 輸出可編譯、測試會過的檔案清單 → 執行站 `passed`、QA 的 prompt 含執行報告、任務完成（整合測試，使用真的 runner 與 `golang` 映像檔）。
- **AC3 失敗退件**：SWE 第一次輸出編譯失敗的程式、第二次修好 → 執行站第一次 `failed` 退回 SWE，退件意見含失敗指令與輸出，第二次 `passed`；`rework_count == 1`。
- **AC4 重做上限**：SWE 每次都輸出編譯失敗的程式 → 任務失敗，原因 `RUN still failing after 3 reworks`（以實際 seat id 為準）。
- **AC5 基礎設施錯誤**：runner 未啟動、映像檔不在允許清單、映像檔不存在 → 執行站 `error`，任務失敗、不重做，原因可讀。
- **AC6 隔離**：在沙盒內嘗試連網失敗；寫入工作區以外的路徑失敗；以 root 身分執行的檢查失敗；超過記憶體或程序數上限的程式被停止；逾時的指令被強制停止且記為失敗；執行結束後 `docker ps -a` 找不到該容器、工作區目錄已刪除；沙盒環境變數中沒有任何金鑰（測試）。
- **AC7 機密檔排除**：專案中有 `.env`、`.git/` 時，沙盒工作區裡沒有它們；SWE 的檔案清單試圖寫入 `../x`、絕對路徑、`.env` → 被拒絕並寫入報告，原始專案資料夾內容在執行前後完全相同（比對雜湊）。
- **AC8 SWE 建議指令**：允許清單內的建議指令被執行並列在報告；清單外的標示「未執行：不在允許清單」；建議指令失敗不會單獨觸發退件。
- **AC9 後端無 Docker 權限**：後端容器內沒有 Docker socket，也沒有 Docker 相關權限（compose 設定測試）；runner API 未帶正確密鑰回 401。
- **AC10 quickstart 不變**：不啟用 runner profile 時 `docker compose up --build` 行為與現在相同；啟用時三個服務以外多一個 runner，健康檢查通過。
- **AC11 畫面**：HUD 上執行站顯示逐指令進度與結果；任務詳情有執行報告；新增 agent 可選 `run`（e2e，使用假 runner）。
- **AC12 歷史與重啟**：執行紀錄在後端重啟後仍可從便條牆與任務詳情看到；執行中重啟後端，任務標 failed，runner 端的工作區在存活時間上限內被清除。
- **AC13 真實驗證（使用者同意、會產生費用，選做）**：重跑 `payment-guardian` tasks.md 第 3 項（Sonnet 5.5，預算上限 2 美元），編制含執行站 → 執行站跑出真實的 `go build`／`go test` 結果，QA 依此判斷，不再因缺執行證據退件。

## Constraints & Assumptions

- 主機有 Docker；runner 需要控制 Docker，這是本功能唯一新增的高權限元件，必須和後端分開。
- 「執行 LLM 寫出的程式碼」與「執行匯入專案的程式碼」都視為執行不受信任的程式碼：live-action-hud spec 的非目標「匯入的程式碼不會被執行」**只在專案明確啟用執行時解除**，預設仍不執行。
- 沙盒無網路，所以相依套件必須在映像檔或專案內；`golang` 範本適用於只用標準函式庫或已 vendor 的專案。
- 安全預設值先採保守數字（例如：每指令 120 秒、整體 300 秒、記憶體 1 GB、1 CPU、256 個程序、每指令輸出 1 MB、交給 QA 的報告 16 KB），實際數字在 plan 決定。
- 只支援 LangGraph 引擎與 DB 模式；`FORCE_MOCK` 與所有測試規則沿用 live-action-hud（驗收一律 `FORCE_MOCK=true`，真實 LLM 呼叫只出現在標明「使用者同意、會產生費用」的步驟）。
- 測試不連網；整合測試需要 Docker（與現有 Testcontainers 測試相同），映像檔需事先拉好或由測試拉取（CI 可接受）。
- 目標機器是開發者本機（macOS／Linux），不是公開服務；runner 不對外開放。

## Open Questions

1. **更強的隔離**：預設只用 Docker 的隔離（無網路、非 root、唯讀、資源上限、移除 capabilities）。是否要支援 gVisor（`runsc`）作為選配？
2. **相依套件**：要不要提供「先在有網路的步驟下載相依，再在無網路的步驟執行」的兩段式模式（例如 Go module proxy）？第一版建議不做。
3. **runner 如何控制 Docker**：掛 Docker socket 給 runner，或用 rootless Docker／Docker-in-Docker？前者最簡單，但 runner 等於拿到主機權限；在 plan 中比較。
4. **SWE 檔案清單的格式**：沿用 Markdown 區塊加路徑標頭，或改用結構化輸出（JSON）？第一版建議與 Mock 共用的文字格式。
5. **執行設定存在哪裡**：DB 的專案設定（可在 HUD 改），或專案資料夾內的檔案（可隨專案版本控制）？可能兩者並存：檔案為初始值，DB 為事實來源。
6. **沒有執行站時 QA 的 prompt**：MVP 的 prompt 調整（告訴 QA「這個環境無法執行程式，請依審查判斷」）是否在本功能完成後，改成只在沒有執行站時才加？
7. **輸出串流**：HUD 要即時顯示指令輸出，還是只顯示每個指令的結果與事後的完整報告？第一版建議只顯示進度與結果。
